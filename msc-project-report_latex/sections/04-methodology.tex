\section{Methodology}\label{methodology}}

\hypertarget{research-approach}{%
\subsection{Research approach}\label{research-approach}}

This work adopts a Design Science Research (DSR) approach (Hevner et
al., 2004). The choice follows from the research question itself. Section~\ref{problem-statement} asks what an active, closed-loop orchestration system buys over a
static passive threshold. That question can only be answered by building 
the artefact and measuring it against the alternatives. It cannot be settled
by observation or by survey because no surveyed system combines the properties
being asked about (Section~\ref{literature-survey}). This is why the DSR approach was chosen.

DSR produces two outputs here. The artefact is the context-aware agentic
gateway. The knowledge contribution is the six-item list of features,
benefits and capabilities set out in Section~\ref{contributions}. Each item there is
checked against a specific evaluation output.

The build-evaluate loop ran three times. The first
trained policy was undertrained and was silently overridden by its own
safety fallback. The second was corrected for that but had no reward
gradient once an SLA was already violated. The third fitted the
\textbf{MiscalibrationClassifier} on non-circular data and retrained the
policy under it. Each cycle was triggered by an evaluation result rather
than by a change of plan, which is the build-evaluate loop working as
intended. All three are reported in Sections 5 and 7.

\hypertarget{deviations-from-the-plan}{%
\subsection{Deviations from the plan}\label{deviations-from-the-plan}}

DSR expects the artefact to change under evaluation. Six planned choices
were not carried.

The proposal specified three independent runs per condition. The
evaluation reports one run per policy per scenario (\textbf{n\_runs=1}). 
Real HuggingFace CPU inference over 1,000 samples for every policy in every 
scenario made three runs unaffordable inside P8's two weeks, and the choice 
was to keep real inference, in place of the repeat count.

The proposal specified energy measurement through Intel RAPL. Energy is
instead a simulated proxy computed in \textbf{environment.py}. RAPL was
never wired in, so no energy number in this report is a hardware power
measurement, and Section~\ref{evaluation-strategy} says so at the point the metric is defined.

The proposal specified the PPO agent as a sidecar pod. Both live
deployments instead co-locate the agent in the same process as the
gateway. Neither is a literal sidecar, and Section~\ref{design-development-and-implementation}'s Deployment
subsection states the distinction plainly.

The proposal specified a TorchServe cloud pod and a Minikube
deployment. Neither was used. The cloud pod is a FastAPI service, and
the Kubernetes path is a three-region GKE deployment.

The proposal specified F1 as the quality metric. Accuracy is reported
instead, because every policy sees the identical capped test set in the
identical order, so the class balance is held constant across all
comparisons and accuracy separates the policies on the same evidence.

\hypertarget{data-and-model-selection}{%
\subsection{Data and model selection}\label{data-and-model-selection}}

The dataset selected for this experiment is Jigsaw toxicity classification
(\texttt{tasksource/jigsaw\_toxicity}, the \texttt{comment\_text} field
against the \texttt{toxic} label). It was chosen because it has a real
difficulty gradient. A weak and a strong model disagree on the
harder comments, so the routing decision has something to be right or
wrong about. A task where both models agree everywhere would make every
routing policy look identical.

The edge and cloud pair is \textbf{DistilBERT}
(\texttt{newsmediabias/DistilBert\_Toxicity\_Classification}) and
\textbf{BERT-large}
(\texttt{AnonymousCS/bert-large-uncased-Twitter-toxicity}), both run on
CPU. The pair was chosen so that the accuracy gap is real and the latency
cost of escalating is also real. Escalation therefore carries a genuine
trade-off rather than a free accuracy gain.

Inference is real HuggingFace CPU inference throughout the evaluation, 
so the accuracy figures  reflect how these two models actually behave on
held-out samples. The dataset is loaded once, shuffled under a fixed seed,
and split 70/10/20 into train, validation, and test. Each evaluation run draws
from the test split at \textbf{max\_samples=1000}, and every policy sees the
same capped set in the same order.

Queue depth, RTT and energy come from the Gymnasium simulation instead
of real infrastructure. Reproducing a saturated cloud queue or a
sustained 800ms RTT reliably on real hardware was not affordable
within this project's timeline. The simulated signal is controllable,
but it still varies between runs, since the simulator draws its own
random stress values each time.

\hypertarget{validity}{%
\subsection{Validity}\label{validity}}

\textbf{Internal validity.} Every comparison uses the same models, the
same dataset and the same scenario settings, and only the routing
policy changes between runs. The simulator's own random stress draws
(CPU, thermal, memory, disk) are not seeded, so each policy's
environment gets its own random sequence instead of an identical one.
A difference in the numbers reflects the routing decision under
matched conditions. This is also the reason why the eight literature
baselines are re-implementations run through this harness, in place of
figures quoted from their original papers.

\textbf{External validity.} Training uses domain randomisation.
\textbf{randomize\_scenario()} resamples twelve \textbf{ScenarioConfig}
fields before every 2,048-step rollout, so the policy sees roughly 49
distinct scenarios across a 100,000-step run instead of one fixed
scenario. The held-out scenario (Ablation Run 6) pushes burst rate,
degraded RTT and cloud service time past the training range, and sets
edge stress and degrade probability right at its edge. The remaining
fields stay inside the range the training rollouts sample. So a good
result there is evidence the policy learned something beyond the
specific scenarios it trained on, even though the test is not
out-of-distribution on every axis.

\textbf{Construct validity.} Four of the eight recorded metrics are terms
in the reward function the policy was trained against. The other four,
escalation rate, fallback rate, SLA margin and trust score are not used 
in the reward function. The second group exists so that a good result can 
be distinguished from the evaluation simply re-measuring the training objective.

\textbf{Reliability.} Each policy is run once per scenario, so no
confidence intervals are reported and no significance test is run. Small
differences should be read as indicative, as opposed to definitive. A gap
of one to two accuracy points on 1,000 samples is within the range a
single run cannot separate from noise, and this report does not treat
such gaps as findings. The claims it does make rest on effects that are
an order of magnitude larger, such as escalation falling from 100\% to
0.5\% and SLA violations from 59.5\% to zero under bursty traffic. Those
are not differences a repeat run would plausibly reverse.

\hypertarget{development-method-and-ethics}{%
\subsection{Development method and
ethics}\label{development-method-and-ethics}}

DSR sets a broad criterion for what counts as valid evidence. It says
nothing about how weekly work should be organised inside each phase. That
is handled by Scrum (Schwaber and Sutherland, 2020), adapted for a single
developer. Sprints are fixed at one week. Each sprint opens with planning
that ties a concrete goal to the current project phase and closes with a
sprint review. Supervisor meetings run weekly, alternating between
mid-sprint check-ins and end-of-sprint reviews. Daily standups are
replaced by a personal daily log entry, since there is no team to
synchronise. Each week's backlog is allocated to one component or one
evaluation run, and the logbook submissions at Weeks 6, 9, 12 and 15
serve as the evidence for each sprint review.

The ethics form was completed and submitted on BREO during P2 (Weeks
2--3). The project involves no human participants and collects no
personal data. Jigsaw is a public dataset used under its existing terms,
and no new data was collected or redistributed. All models are
pre-trained checkpoints obtained from the HuggingFace Hub and used
without modification. The synthetic clients in Ablation Run 7
(\textbf{client\_nhs}, \textbf{client\_babcock} and the others) are
fictional load profiles. No real organisation or its data is
involved.
