\hypertarget{edge-context-protocol}{%
\subsection{Edge Context Protocol}\label{edge-context-protocol}}

\hypertarget{design}{%
\subsubsection{Design}\label{design}}

\textbf{ResourceStress} records edge health as five separate numbers:
cpu, gpu, memory, disk\_io, and thermal, each between 0 and 1. CPU and thermal stress degrade confidence
calibration, so the model becomes confidently wrong. Memory and disk
pressure degrade \emph{latency} instead, which is an SLA risk. A single
scalar cannot separate a slow-but-correct edge from a fast-but-wrong
one. EdgeBERT (Tambe et al., 2021) is the only system in Section~\ref{literature-survey} that
reads any on-device resource state at all, and even it is restricted to
its own chip's entropy/voltage-frequency envelope, with no per-resource
breakdown. BranchyNet, MSDNet, RouteLLM, GreenServ, and both production
gateways read no device resource state at all. The five-field design is
a direct response to that gap.

\hypertarget{implementation}{%
\subsubsection{Implementation}\label{implementation}}

The \textbf{EdgeDevice} module acts as an interface that transforms raw
readings from device resources into a self-report of its condition.
\textbf{ResourceMonitor.sample()} takes readings from physical
parameters of the device (cpu\_percent, virtual\_memory().percent,
disk\_usage().percent) via \textbf{psutil}. \textbf{thermal} comes from
\textbf{psutil.sensors\_temperatures()} and is scaled down assuming a maximum
operating temperature of 85\textdegree{}C. If there is no sensor for a certain reading, the system falls back to
0.0. A cloud VM is one example of a device with no sensors.
\textbf{edgeDevice.apply\_stress()} lets the offline simulator inject
synthetic values over the same code path that \textbf{emit\_report()}
consumes. This makes the handling of simulated and real stress
completely uniform.

\textbf{EdgeDevice.emit\_report()} is the core of the protocol. Besides
an inference's raw confidence, it computes a calibrated confidence by
calling \textbf{compute\_calibration\_delta()}, which applies
temperature scaling (Guo et al., 2017). The temperature term is itself
a function of the sensed stress (\textbf{temp = 1.0 + 0.5*cpu + 0.3*thermal}).
So higher stress pulls the calibrated confidence closer to 0.5. This
directly targets the failure mode Guo et al. describe, and the one the
introduction's problem statement opens with. A model's raw softmax
confidence stays high while the prediction underneath it degrades under
load. BranchyNet and MSDNet both read raw softmax confidence or entropy
as if it were trustworthy at every stress level, with no correction
term at all. That is the exact gap this calibration step closes.
\textbf{emit\_report()} also keeps an operating error buffer (a
60-sample rolling buffer for \textbf{error\_rate}) and classifies
\textbf{operational\_state} by calling
\textbf{MiscalibrationClassifier.predict()}.

\hypertarget{classifier-status}{%
\subsubsection{Classifier status}\label{classifier-status}}

\textbf{MiscalibrationClassifier} is a logistic regression over the
stress vector and error rate. \textbf{.fit()} has now been called on
real, non-circular data, in two separate domains. Its labels come only
from real observed accuracy relative to an idle baseline, never from
the fallback heuristic \textbf{\_fallback\_heuristic()} it replaces.
That heuristic still stays available as the untrained default. It fires
DEGRADING when CPU\_thermal \textgreater{} 0.85 or error\_rate
\textgreater{} 0.10, and STRESSED when CPU\_thermal \textgreater{} 0.65
or memory \textgreater{} 0.80 or disk \textgreater{} 0.80.

The first attempt trained on real hardware, under genuine
\textbf{multiprocessing}-induced CPU stress. It used 80,139 samples and
a class-weighted logistic regression, with DEGRADING gated behind a
precision/recall-tuned probability threshold over plain argmax.
This gave 68.0\% $\pm$ 2.6\% balanced accuracy, and 64.4\% DEGRADING
precision at 66.4\% recall, 5-fold cross-validated. But it does not
transfer into the Gymnasium simulation. This was confirmed after
counting predicted \texttt{operational\_state} across live simulated
steps. It predicts NOMINAL on 100\% of inputs because its
decision boundary was fit on real \textbf{psutil} value ranges that do
not overlap the simulation's synthetic stress distribution.

In the second attempt, it was retrained with the same methodology. The
simulation's own synthetic stress formula was used in the second attempt.
It used 27,000 samples and the same threshold-tuning approach. This gave 
54.6\% $\pm$ 2.0\% balanced accuracy, weaker than the real-hardware fit, 
particularly on STRESSED precision (33.2\%). The same direct check confirms
this one does transfer. It produces state
distribution that rises with scenario stress the way it should. It also shows
2.75\% DEGRADING under steady traffic. Under the held-out scenario, it rises 
to 5.15\%. Every evaluation after this section uses this classifier
by default (\textbf{environment.py}, unless \textbf{DEVMIND\_MISC\_CLASSIFIER\_PATH}
overrides it). Wiring it in also changes routing behaviour by a lot. The policy
escalated far more often under the old heuristic. With the trained classifier,
escalation dropped to between 15\% and 18\% of that old rate in every scenario,
while accuracy stayed about the same. Section~\ref{misc-classifier-refit} repeats
the same swap against the retrained policy, where the gap is much
smaller, and separates the two effects. That is because the heuristic's fixed 0.65
STRESSED threshold sits well inside the simulation's own ``stressed''
value range, and fires far more often than the trained classifier does.
Full methodology and numbers are in
\textbf{evaluation/misc-classifier-fit-2026-09-01.md}. It also states a
limitation: this behavioural improvement reflects suppressing the
heuristic's false alarms. It is not evidence of a demonstrably more
accurate classifier.

\hypertarget{deadmans-switch}{%
\subsubsection{Deadman\textquotesingle s switch}\label{deadmans-switch}}

\textbf{EdgeDevice.is\_unreachable} is defined as a property. It stays
unreachable until there is a \textbf{\_last\_seen}, and again once
\textbf{time.monotonic() - \_last\_seen \textgreater{} stale\_timeout\_s}. Two
independent paths can trigger it. One calls \textbf{mark\_unreachable()}
directly, usually when the edge inference call times out or raises an
error. The other is passive. It fires if neither a request nor a
\textbf{heartbeat()} updates \textbf{\_last\_seen} within the timeout
window. \textbf{last\_report} overwrites the stored
\textbf{operational\_state} to \textbf{UNREACHABLE} whenever
\textbf{is\_unreachable} is true. This guarantees no stale values are
ever served as current.

The live gateway (\textbf{gateway/app.py}) executes a
\textbf{\_heartbeat\_loop} at 2-second intervals, separate from the
request traffic.

None of the twelve systems in Section~\ref{literature-survey}, academic or commercial, has a
counterpart to this. Confidence- and budget-only cascades have no
concept of edge liveness at all. LiteLLM's cooldown and Portkey's
failover both react only to a request that has already failed.
Neither reacts to a device that has gone silent without failing
anything yet. This
distinction matters in practice. A deadman's switch transforms
``no data'' into a clear state of \textbf{UNREACHABLE}. The 
routing decision can respond to such state even before the next 
request. It does not have to wait for the request to time out first.

\hypertarget{bronze}{%
\subsubsection{Bronze}\label{bronze}}

\textbf{DynamicMetricRegistry} is a dictionary of
\textbf{MetricSource(name, schema\_type, read\_fn)} entries, following
the registration-based extensibility pattern for adding behaviour
without modifying existing consumers (Gamma et al., 1994).
\textbf{snapshot()} pulls data from the registered sources and matches
names to build the \textbf{BronzeMetricSnapshot}. Adding a new source
only needs \textbf{registry.register(...)}. It needs no code changes to
\textbf{SilverEnricher} or \textbf{GoldNormalizer}.
\textbf{cloud\_queue\_depth} and \textbf{rtt\_ms} come from the real
HTTP client in the live gateway, through \textbf{cloud\_client.inflight}
and \textbf{cloud\_client.rtt\_ms}, as actual measured values from the
HTTP client to the cloud pod.

Every system surveyed in Section~\ref{literature-survey} hardcodes its one signal at design
time (BranchyNet's entropy threshold, MSDNet's computational budget,
PROTEUS's accuracy target, LiteLLM's and Portkey's operator-set
weights). So adding a new signal means changing the routing
algorithm itself. A registry entry adds a value without touching
\textbf{SilverEnricher} or \textbf{GoldNormalizer}, which is the direct
answer to that limitation. But there is a caveat, extending Gold's 13-slot
layout for a new signal still means editing \textbf{snapshot()}'s match-case.
So the registry is dynamic at the value level.

\hypertarget{silver}{%
\subsubsection{Silver}\label{silver}}

\textbf{SilverEnricher.enrich()} computes two predictive features. One is
\textbf{predicted\_queue\_wait\_ms}, which is an EWMA (alpha=0.3) of the
drain rate, \textbf{cloud\_queue\_depth} divided by
\textbf{sla\_remaining\_ms}, then multiplied back into
\textbf{sla\_remaining\_ms}. The other is \textbf{predicted\_rtt\_ms}, an
EWMA (alpha=0.2) of sampled RTT.

\textbf{This is a computed signal.}
Tracing every read of \textbf{sla\_violation\_predicted} across the code 
confirms that it is set here and not read by \textbf{GoldNormalizer},
 \textbf{AgenticOrchestrator.decide()}, or \textbf{CascadeController.process()}.
\textbf{sla\_remaining} and \textbf{predicted\_rtt} are the two Gold slots
that reach the routing decision instead. The PPO policy is trained using the reward
function's SLA terms. That is why it is a single-request \emph{signal} through
which the agent is supposed to learn to act. It is not a deterministic
barrier that blocks an escalation the way \textbf{sla\_violation\_predicted}
would. The one hard, rule-based gate in the whole system is narrower, and
it lives in the safety fallback. \textbf{\_resolve\_fallback()}'s
\textbf{queue\_backed\_up} guard (below) routes to edge when predicted
queue wait exceeds a ceiling. But it does not guard on every request.
It activates only when the fallback path itself is triggered (entropy or OOD).
Wiring \textbf{sla\_violation\_predicted} into \textbf{decide()} as an
unconditional pre-dispatch check would be the harder guarantee the
project proposal originally described. That remains open work. It is
not a claimed result.

Enrichment is conditional on \textbf{operational\_state},
\textbf{calibration\_delta} is only populated when \textbf{STRESSED} or
\textbf{DEGRADING}, \textbf{error\_rate} only when \textbf{DEGRADING}.
The default value is \textbf{None}. When the edge is
\textbf{UNREACHABLE}, \textbf{stale=True} is set, which zero-masks the
resource-stress slots downstream instead of serving a stale last-known
reading.

\hypertarget{gold}{%
\subsubsection{Gold}\label{gold}}

\textbf{GoldStateVector.from\_silver()} builds a fixed 13-slot layout:

\begin{samepage}
\begin{itemize}
\item[0.] \textbf{confidence}
\item[1.] \textbf{predicted\_queue\_wait}
\item[2.] \textbf{predicted\_rtt}
\item[3.] \textbf{sla\_remaining}
\item[4.] \textbf{edge\_cpu\_load}
\item[5.] \textbf{resource\_cpu}
\item[6.] \textbf{resource\_gpu}
\item[7.] \textbf{resource\_memory}
\item[8.] \textbf{resource\_disk\_io}
\item[9.] \textbf{resource\_thermal}
\item[10.] \textbf{calibration\_delta}
\item[11.] \textbf{error\_rate}
\item[12.] \textbf{operational\_state}
\end{itemize}
\end{samepage}

\textbf{mask{[}10{]}} and \textbf{mask{[}11{]}} are zeroed
exactly when Silver set \textbf{calibration\_delta} or
\textbf{error\_rate} as \textbf{None}. \textbf{stale=True} additionally
zero-masks slots 4 through 10 (edge\_cpu\_load through
resource\_thermal). The PPO policy is always fed the full 13-dim
vector. Masking communicates \emph{absence}, it does not shrink the input.
This is what lets the same trained network handle \textbf{NOMINAL},
\textbf{STRESSED}, \textbf{DEGRADING} and \textbf{UNREACHABLE} states
without retraining per state.

\hypertarget{mcp-skill-interface}{%
\subsection{MCP Skill Interface}\label{mcp-skill-interface}}

\hypertarget{implementation-1}{%
\subsubsection{Implementation}\label{implementation-1}}

The \textbf{MCPSkillInterface} in agent.py keeps a dictionary of
boolean flags, one per skill, across eight skill groups. Five of these
are active by default: \textbf{get\_model\_confidence},
\textbf{get\_cloud\_queue\_depth}, \textbf{get\_edge\_rtt},
\textbf{get\_sla\_remaining} and \textbf{get\_edge\_cpu\_load}. The
other three, \textbf{get\_edge\_calibration\_delta},
\textbf{get\_edge\_error\_rate} and
\textbf{get\_edge\_operational\_state}, stay inactive until
\textbf{register\_skill()} is called. \textbf{list\_tools()} only
returns the currently active names. Every skill's \textbf{call()} just
fetches the relevant element of the Gold vector, which is already
computed and stored in memory. There is no network call and no
recomputation, so the perception cycle stays cheap by construction.

This was benchmarked directly against real DistilBERT CPU inference
(\textbf{benchmark\_mcp\_perception.py}, 300 requests, the same
component wiring as the live gateway's \textbf{CascadeController}).
Perception, meaning Bronze to Silver to Gold to \textbf{decide()}
including the skill interface, averages 0.57ms (p95 0.97ms). Mean edge
inference latency is 23.9ms, so perception is about 2.4\% of it,
comfortably inside the per-request perception budget.

None of the twelve systems in Section~\ref{literature-survey} exposes its signals this way.
BranchyNet, MSDNet, EdgeBERT and PROTEUS bake their one signal directly
into the routing function. Even the two production gateways only
expose configuration options to an operator. Neither offers a
discoverable, callable interface a policy can query for itself at
request time.

\textbf{MCPSkillInterface} mimics MCP's discovery and registration shape,
 a Python class with a dictionary of named, activatable capabilities and
a \textbf{list\_tools()} method. This helps avoid a dedicated http MCP server
which will add latency to the request flow.

Earlier designs had \textbf{AgenticOrchestrator.decide()} run a second
forward pass through the policy after the extended skills were
registered, to handle \textbf{QUERY\_EXTENDED\_CONTEXT}. It was replaced
with \textbf{SilverEnricher.enrich()}. This function computes
\textbf{calibration\_delta} and \textbf{error\_rate} from the edge's
real \textbf{operational\_state}, already runs before \textbf{decide()}
does. So the Gold vector the policy sees is identical in both calls, and
a second forward pass on the same input adds nothing but random
sampling noise from the policy head.

Instead, \textbf{decide()} resolves \textbf{QUERY\_EXTENDED\_CONTEXT} by
asking \textbf{act()} to register the extended skills. It then queries
\textbf{get\_edge\_calibration\_delta()} and
\textbf{get\_edge\_error\_rate()} directly, and applies a hardwired risk
rule. If either is above threshold (0.2 or 0.15), it escalates to
cloud. Otherwise it sends to edge.

One feature remains incomplete: a querying action-dependent
masking mechanism, the key of the ``query-conditional reveal''
ideology. Under it, concealment of the signal would be a function of which
skill was queried, instead of only the operational state. Creating this would mean
that the PPO learning loop from which only the raw data is obtained, i.e.
\textbf{policy.forward()} with which a \textbf{decide()} is totally
bypassed, would be the only ones to learn the reveal protocol. Such a change
was beyond the scope of this project.

\hypertarget{ppo-agent}{%
\subsection{PPO Agent}\label{ppo-agent}}

\hypertarget{training}{%
\subsubsection{Training}\label{training}}

PPO (Schulman et al., 2017) was chosen over the other standard
policy-gradient candidates for reasons specific to this project,
rather than because PPO happens to be popular.

DQN is a poor fit for one specific reason. The safety fallback in
\textbf{AgenticOrchestrator.decide()} triggers when
action entropy goes above 0.9. That needs the policy to be an explicit
stochastic distribution over actions at every decision. DQN's
$\epsilon$-greedy action selection over learned Q-values has no
equivalent per-decision entropy signal, so the entropy-gated fallback
this project depends on would have to be built separately, instead of
falling naturally out of the training objective.

SAC is a poor fit for a different reason. Its maximum-entropy machinery
(twin Q-networks, a reparameterised continuous policy) is built for
continuous action spaces and buys nothing over a 3-action discrete space
like this one.

Against vanilla actor-critic (A2C) or TRPO, PPO's clipped surrogate
objective approximates TRPO's trust-region constraint without TRPO's
second-order Hessian computation, and it is also less sensitive to
learning-rate choice than A2C, which matters on a CPU-only training
budget with no room for a hyperparameter sweep.

\textbf{PPOTrainer}'s advantage estimates use Generalized Advantage Estimation
(Schulman et al., 2016), the same $\lambda$-weighted exponential average
of $n$-step temporal-difference residuals that was introduced alongside
PPO's own lineage of trust-region methods. GAE is used here, in place of
a plain one-step or full Monte-Carlo advantage because the reward is
noisy at the level of a single request, a per-request weighted sum of
four objectives (accuracy, SLA, energy, latency, see Section~\ref{evaluation-strategy}). The
$\lambda$ parameter trades that per-step noise against the bias of
bootstrapping from the value head, and that trade-off matters on the
100,000-step training budget this project can actually afford, where a
higher-variance estimator would need substantially more rollouts to
converge.

\textbf{PPOTrainer} (\textbf{trainer.py}) is a standard PPO training loop.
\textbf{train\_agent()} adds domain randomization (Tobin et al., 2017).
\textbf{randomize\_scenario()} resamples 12 \textbf{ScenarioConfig} fields (traffic
rates and timing, RTT, edge stress/degrade/unreachable probabilities,
cloud service time) from a seeded RNG before every 2048-step rollout, so
the policy sees roughly 49 distinct sampled scenarios across a
100,000-step run rather than one fixed scenario.

Domain randomization was chosen over training on a single fixed
scenario for a specific reason. The project's target evaluation
condition, \textbf{ScenarioConfig.held\_out()}, is deliberately built to sit
outside anything seen in training
(Section~\ref{evaluation-strategy}). Tobin et al. (2017)
show that randomizing simulation parameters widely enough can make a
novel condition look, to the trained policy, like just
another sampled variation, as opposed to a distribution shift. Ablation
Run 6 tests this claim directly, instead of just assuming it, since it
is the run that evaluates the trained policy against \textbf{held\_out()} and
reports whether performance degrades gracefully or collapses.

An initial 50,000-step run left the policy undertrained. Action entropy
on real inference traffic stayed pinned above the 0.9 fallback
threshold, so every routing decision was silently overridden by
\textbf{\_resolve\_fallback()} instead of the trained policy
(\textbf{fallback\_rate=1.000} across all scenarios). This was found by
instrumenting a short training rollout directly. Entropy was declining
normally, 1.097 $\to$ 1.082 $\to$ 1.028 over the first three rollouts,
an accelerating rate, but it simply had not crossed 0.9 by 50,000
steps. That is evidence of undertraining. It is not evidence of a
broken reward or a stuck policy. Doubling the run to 100,000 steps fixed this.
\textbf{fallback\_rate} dropped to 0.000 across all scenarios,
confirming it is now the policy's own action that gets dispatched.
The fixed fallback rules no longer override it.

A second issue surfaced once the fallback was confirmed to be off.
The retrained policy still escalated to cloud 81.5\% of the time
under the degraded-network scenario. That made no sense: every policy
tested there, including \textbf{always\_edge}, already hits
\textbf{sla\_violation\_rate=1.000}, because RTT alone (800ms)
exceeds the 300ms SLA budget no matter how the request is routed.
Escalating in that scenario cannot help. It was paying roughly
4$\times$ the latency and 3$\times$ the energy of edge-favouring
baselines, for no accuracy gain.

The root cause was in the reward function. It was not the policy. The latency
term in \textbf{\_compute\_reward()} (\textbf{environment.py}) was
\textbf{max(0.0, 1.0 - latency/sla\_budget)}, floored at zero once
latency exceeds the budget. So the reward was identical whether an
action's latency was 1ms or 1000ms over budget. That gave the policy no
gradient to prefer the less-bad option once the SLA was already lost.

The fix was to remove the floor, using
\textbf{1.0 - latency/sla\_budget} unclamped (the outer
\textbf{np.clip(reward, -1, 1)} in \textbf{step()} still bounds the
total). Retraining for a further 100,000 steps reduced degraded-network
escalation from 81.5\% to 21.5\%, energy from 365.0 to 178.4, and p95
latency from 1067.8ms to 950.7ms.

The effect was broader than the narrow case it targeted. Escalation
rate fell from roughly 85\% to roughly 20\% in every scenario. The
effect reached beyond the degraded-network case it targeted. SLA violations under bursty traffic fell from
65.5\% to 0.0\%, and energy consumption dropped 50--80\% across the
board. The accuracy cost was small and consistent, 0.5--2 percentage
points per scenario. Full before/after figures per scenario are given
in the Evaluation and Discussion section. At this point the
degraded-network over-escalation was reduced, but not eliminated. The
policy still escalated a fifth of the time, in a scenario where
escalating provably buys nothing.

This policy is still not the one the Evaluation and Discussion section
reports. The residual over-escalation turned out to be driven less by
the reward function than by what the policy was being told about the
edge. Once \textbf{MiscalibrationClassifier} was fitted (above) and made
the simulation default, the policy was retrained from scratch for a
further 100,000 steps in that environment. Degraded-network escalation
fell again, from 21.5\% to 1.5\%. That retrained policy is what every
number in Section~\ref{evaluation-and-discussion} reports. Section~\ref{misc-classifier-refit} separates how much of the
improvement belongs to the trained classifier and how much to the
retraining itself. The residual 1.5\% is still reported as a previously discussed
limitation. It is not treated as a fully closed issue.

\hypertarget{safety-fallback}{%
\subsubsection{Safety fallback}\label{safety-fallback}}

\textbf{AgenticOrchestrator.decide()} (\textbf{agent.py}) checks two independent
conditions before it trusts the policy's sampled action. One is action
entropy above 0.9. The other is \textbf{is\_ood()}, a z-score check against
saved training statistics (\textbf{state\_stats.json}). This check requires
two slots to be simultaneously anomalous
(\textbf{OOD\_MIN\_ANOMALOUS\_SLOTS=2}), and it floors each
slot's std (\textbf{OOD\_STD\_FLOOR=0.02}). That floor stops a near-constant
training signal, for example \textbf{sla\_remaining} when the SLA budget never
varies in training, from dominating the check on a floating-point-scale
deviation.

Either condition routes the decision to \textbf{\_resolve\_fallback()}, an
ordered list of named guards evaluated first-match-wins.
\textbf{queue\_backed\_up} runs first: it routes to edge if predicted queue
wait exceeds a per-instance \textbf{fallback\_queue\_wait\_ceiling}, avoiding
escalation into an already-collapsing queue. \textbf{low\_confidence} runs
next, escalating if confidence is below 0.9. Otherwise the default is
route-to-edge. The ceiling is an instance attribute rather than a
class constant, specifically so it can be recalibrated per client without
touching the guard list's structure.

\hypertarget{why-the-fallback-is-deliberately-simple}{%
\subsubsection{Why the fallback is deliberately
simple}\label{why-the-fallback-is-deliberately-simple}}

The fallback is an emergency measure, engaged when the policy's own
output is not trustworthy. Relying on it more heavily would mean
introducing another learned or more complex system. That would just
move the trust problem up a level instead of solving it.

RouteLLM (Section~\ref{literature-survey}) is described purely as a fitted router. A request
is routed by whatever the model outputs, with no uncertainty check or
out-of-distribution check reported as part of the routing decision
itself. The entropy/OOD gate exists so that a bad policy
output degrades to a fixed, auditable rule. This is the same pattern that later caught the meta-policy's
failure to converge (below), instead of letting it silently make
governance decisions.

\hypertarget{cascade-controller}{%
\subsection{Cascade Controller}\label{cascade-controller}}

\textbf{CascadeController.process()} runs the forward pass for a single
request. First it applies a 2-second edge inference timeout, calling
\textbf{mark\_unreachable()} on failure. Then it calls
\textbf{emit\_report()} and runs Bronze, Silver and Gold. Then it calls
\textbf{agent.decide()}, then \textbf{\_dispatch()}, then
\textbf{reflect()} and \textbf{update\_from\_outcome()}. Edge inference,
edge self-reporting, and the agent's decision all happen in the same
process, without crossing a network boundary. The only real network
call in the whole request path is when \textbf{\_dispatch()} calls
\textbf{CloudClient.predict()} for action \textbf{ESCALATE\_TO\_CLOUD}.
\textbf{\_dispatch()} retries the cloud call once on failure. If it
still fails, it uses the already computed edge result
(\textbf{edge\_fallback\_cloud\_unreachable}) instead of failing the
request outright.

\hypertarget{bidirectional-loop}{%
\subsection{Bidirectional Loop}\label{bidirectional-loop}}

The forward pipeline: \textbf{edge\_model.predict()} $\rightarrow$ \textbf{edge.emit\_report()} $\rightarrow$
Bronze $\rightarrow$ Silver $\rightarrow$ Gold $\rightarrow$ \textbf{agent.decide()} $\rightarrow$ \textbf{\_dispatch()}.

The backward pipeline works like this. \textbf{agent.reflect(latency,
sla\_met, accuracy, tier, fallback)} logs the outcome to the memory
buffer. \textbf{edge.update\_from\_outcome(latency, sla\_met, accuracy)}
updates the edge device's rolling error buffer and a slow (alpha=0.05)
trust EWMA. Only the next request's Bronze snapshot can see these
updates. The current one cannot. None of these steps change the weights of
the PPO policy.

This closes a gap that every system in Section~\ref{literature-survey} leaves open. That
includes more than just the cascade baselines. EdgeBERT's DVFS adapts within a single request,
and GreenServ's bandit adapts across requests, but neither feeds a
routing outcome back into the state of the specific device that served
it. GreenServ's update changes which model the \emph{next arbitrary
query} gets routed to. It does not change what the edge device itself
now reports about its own condition. Ablation Run 4 (Section~\ref{ablation})
measures the effect of removing this loop directly, instead of leaving
its value as an architectural claim.

\hypertarget{policy-orchestration-layer}{%
\subsection{Policy Orchestration
Layer}\label{policy-orchestration-layer}}

The \textbf{PolicyOrchestrator} only runs during onboarding and drift
detection, never on every request. Its fleet-level value is measured
directly here, as opposed to just asserted. In a four-client onboarding trial,
the governance review escalated one under-provisioned decision that the
deterministic rule alone would have accepted (Ablation Run 7, Section~\ref{ablation-run-7}).

The \textbf{onboard()} function evaluates every policy in the library
against the new client's scenario, over 3 episodes, using
\textbf{\_evaluate()}. \textbf{select\_decision()} and then chooses between
three levels of action. If the client already has a policy that meets
all the tolerance thresholds, it reuses it (\textbf{REUSE}). If the
client's closest candidate just needs some adjustment, it fine-tunes it
(\textbf{FINE\_TUNE}). If the scenario is completely new, it trains a
new policy (\textbf{TRAIN\_NEW}). That training uses the same
domain-randomization function, \textbf{randomize\_scenario()}, as
top-level seed-policy training. So a fine-tuned or newly-created
per-client policy is never held to a lower standard than the shared
one.

The REUSE/FINE\_TUNE/TRAIN\_NEW decision is the task-capacity promotion
test described by Bossens and Sobey (2021). It decides whether an
existing policy already covers a new task, before spending a full
training run on it. Here it is applied at the level of a whole fleet of
onboarding clients, in place of a single agent's sequential task
stream. Neither LiteLLM nor Portkey (Section~\ref{literature-survey}) has anything resembling
this. Both route traffic across a fixed, operator-configured set of
providers or models, with no mechanism for deciding whether an existing
policy already serves a new client well enough, needs adapting, or
needs replacing. If that decision exists at all in a production gateway
today, a person reading a dashboard makes it. The system itself does
not.

\textbf{\_log\_decision()} stores every decision and its supporting
metrics to orchestrator\_decisions.jsonl. This includes the tolerance
gap (\textbf{dominant\_signal}) that drove the decision, which is one
of the most important pieces of the ``how and why'' explanation this
project provides.

\hypertarget{fallback-threshold-calibration}{%
\subsubsection{Fallback-threshold
calibration}\label{fallback-threshold-calibration}}

\textbf{calibrate\_fallback\_ceiling()} adjusts the fallback
mechanism's client-specific \textbf{fallback\_queue\_wait\_ceiling}
based on that client's own usage history. It tightens when the
client's \textbf{fallback\_rate} is high (above 0.3), and loosens when
the client rarely triggers the fallback (below 0.05). This is the same
model \textbf{recalibrate\_thresholds()} already uses to govern the
reuse/fine-tune/train-new tolerances from historical evidence.

This computed value is not yet consumed live, in the same sense
\textbf{DriftEventListener} is not (above). \textbf{gateway/app.py}
builds each client's \textbf{AgenticOrchestrator} without reading
\textbf{orch.fallback\_ceilings{[}client{]}} back into it. So the
calibration is computed and logged, but it does not yet reach the
running gateway process. Every such adjustment is logged the same way.

\textbf{DriftEventListener.should\_escalate()} looks at two signals
together. A client in sustained distress, reporting
\textbf{DEGRADING} or \textbf{UNREACHABLE} while its trust score stays
low, only triggers \textbf{onboard()} once that state has persisted for
\textbf{recovery\_window\_s}. A spike in error rate overrides this and
escalates immediately, as long as the client-specific cooldown has
elapsed. Together, these two rules mean a genuine spike is not held
back for the full sustained-distress window, and does not re-trigger on
every request during an outage.

While extending the governance layer described below,
\textbf{DriftEventListener} was found to be unwired in the live
gateway. \textbf{gateway/app.py} never constructs one or passes it to
\textbf{CascadeController}, which accepts an optional
\textbf{drift\_listener} that stays \textbf{None} in production today.
Its shape, a non-blocking \textbf{put\_nowait()} onto an
\textbf{asyncio.Queue}, consumed by an async \textbf{run\_forever()}, is
correct and is only exercised by its own self-check. It is treated here
as built-but-not-yet-live infrastructure. It is not an active
production path.

A separate, simpler path was since wired in for the request-triggered
case. In \textbf{CascadeController.process()}'s \textbf{except} block,
the same failure that calls \textbf{mark\_unreachable()} also drives
\textbf{\_unreachable\_fallback()} to log the fallback to
\textbf{request\_log.jsonl} with
\textbf{fallback\_reason="edge\_unreachable"}.
\textbf{orchestrator\_app.py}'s \textbf{\_tail\_action\_log\_loop},
already polling that file every 1.5 seconds for other purposes, now
recognises that reason and broadcasts an urgent notification over the
\textbf{/ws} websocket to any open dashboard session, through the same
panel the LLM-diagnosis alerts use. This does not depend on
\textbf{DriftEventListener} and does not need \textbf{gateway/app.py}
to construct one; it fires whenever \textbf{\_unreachable\_fallback()}
runs.

This closes the gap for a request that reaches
\textbf{CascadeController} and finds the edge unreachable. It does not
close it for silence. An edge that goes unreachable and then simply
receives no further requests is still only visible through the
heartbeat-maintained \textbf{is\_unreachable} property
(Section~\ref{deadmans-switch}), which nothing polls or pushes on its
own. The notification above fires from inside a request's own
\textbf{except} path, not from the heartbeat loop.

\hypertarget{per-client-thresholds}{%
\subsubsection{Per-client thresholds}\label{per-client-thresholds}}

A company can set its own onboarding bar instead of inheriting the
shared default. \textbf{PolicyOrchestrator.set\_client\_thresholds()}
stores a per-client \textbf{ToleranceThresholds} override.
\textbf{\_thresholds\_for(client)} resolves override-or-default
everywhere \textbf{onboard()} used to read the shared
\textbf{self.thresholds} directly. \textbf{recalibrate\_thresholds()}
still only drifts the shared default, so a client that set its own bar
is not silently moved by the aggregate false-reuse rate observed across
other clients. This is exposed on the dashboard through optional
\textbf{max\_sla\_violation\_rate}, \textbf{max\_escalation\_rate} and
\textbf{min\_accuracy} fields on \textbf{POST /clients}.

\hypertarget{llm-backed-diagnosis}{%
\subsubsection{LLM-backed diagnosis and live
monitoring}\label{llm-backed-diagnosis}}

Two related capabilities were added to make the orchestrator explain
itself, going beyond simply logging a decision. Both call a small local model (Ollama,
\textbf{gemma4:12b-it-qat}) through \textbf{diagnosis.py}'s
\textbf{DiagnosisProvider} abstraction, entirely off the request path.
Neither diagnosis output feeds back into
\textbf{AgenticOrchestrator.decide()} or any routing decision, so the
per-request PPO's determinism claim is untouched.

\textbf{EscalationDiagnosisMonitor} watches per-client action-log rows
(the same queue-plus-cooldown shape as \textbf{DriftEventListener}). When
a client's escalation rate stays $\geq$95\% over a 50-request rolling
window, it asks the LLM to explain \emph{why} and \emph{what resource is
needed}, and the dashboard broadcasts the result over a websocket
alongside a real-time escalation chart, tailed from
\textbf{request\_log.jsonl} by byte offset.

\textbf{\_diagnose\_unreachable\_threshold()} answers a narrower
question. After a fresh FINE\_TUNE or TRAIN\_NEW, if the policy trained
specifically for that scenario still misses the client's threshold,
that is evidence the requirement itself may be unreachable for that
scenario, for example because RTT alone already exceeds the SLA
budget. It is not evidence that training just needs another attempt.
The same diagnosis provider is then asked whether the requirement is
realistic, and what changes should be made.

\hypertarget{learned-meta-policy-attempted}{%
\subsubsection{A learned meta-policy for onboarding decisions,
attempted and superseded}\label{learned-meta-policy-attempted}}

The REUSE/FINE\_TUNE/TRAIN\_NEW decision above is a deterministic
threshold rule. To make it learn instead,
\textbf{orchestrator\_trainer.py} built
\textbf{OrchestrationDecisionEnv}. It runs one synthetic onboarding
decision per episode, framed as an episode-length-one MDP, so that
\textbf{PPOTrainer}/\textbf{PPONetwork} can be reused completely
unmodified. The reward is always computed from a genuine evaluation of
whichever action was actually taken. REUSE evaluates the real seed
policy. FINE\_TUNE and TRAIN\_NEW actually run a short training run,
then evaluate the result. The reward was never a fabricated number,
only the training budget during meta-training was reduced, to keep
rollout collection tractable.
\textbf{PolicyOrchestrator.\_meta\_decide()} wired this in with the
same entropy/OOD safety fallback that
\textbf{AgenticOrchestrator.decide()} already uses.

It did not converge. Each step took roughly 47 to 75 seconds, because
every step was a real evaluation or a real short training run. None of
it is a cheap simulated transition. After 160 real training steps, entropy
stayed above the 0.9 fallback threshold on every one of four real test
clients. Every governance decision silently fell back to the
deterministic rule. A later comparison run produced identical decisions
with and without the meta-policy configured, because the learned path
never actually engaged.

Matching the per-request PPO's own 100,000-step convergence point, at
this measured rate, would take time beyond this project's scope,
which is not tractable under this design. The per-request PPO's simulated environment steps
are near-free, but this meta-environment's steps are expensive by
design, because the reward is never fabricated. Full numbers and logs
are kept in \textbf{evaluation/option-b-meta-policy-failure-2026-08-24.md},
and the code stays in the repository, in place of being deleted. The
safety fallback caught the failure exactly as intended, instead of
silently authorising a bad governance decision. That is itself evidence
the entropy/OOD-gated pattern works, even though this particular
learned component's training economics did not.

\hypertarget{llm-governance-review}{%
\subsubsection{LLM governance review}\label{llm-governance-review}}

This is what replaced the meta-policy attempt.
\textbf{PolicyOrchestrator.\_governance\_review()} lets the same local
LLM review the rule's (or meta-policy's) decision. It can only ever
\emph{escalate} that decision to a more cautious action (REUSE $\to$
FINE\_TUNE $\to$ TRAIN\_NEW), never downgrade it. So a hallucinated
review can waste computing resource at worst. It can never silently authorise an
under-provisioned policy. The review is skipped entirely once the
decision is already TRAIN\_NEW, since there is nothing more cautious to
escalate to, and it is a no-op when no diagnosis provider is
configured.

The review was live-tested against a real Ollama instance, using a
simulated onboarding client's numbers. A seed policy measured
\textbf{sla\_violation\_rate=1.00} against a \textbf{0.15} requirement,
and the deterministic rule chose \textbf{fine\_tune}. The review
correctly escalated the decision to \textbf{train\_new}, justifying it
as ``the seed policy's sla\_violation\_rate of 1.00 significantly
exceeds the maximum allowed threshold of 0.15''. This took roughly 2.5
seconds once the local model was warm. An earlier attempt against a
cold Ollama had exhausted both retries at the raised 20-second timeout,
40 seconds in total. That was an
operational quirk of the LLM being idle-unloaded. It was not a code
defect.

A four-client onboarding run with governance review enabled confirmed
three clients' REUSE decisions without wasting compute, and escalated
the one client whose seed policy missed its SLA requirement by
a wide margin. This is discussed further as Ablation Run 7 in the
Evaluation and Discussion section.

\hypertarget{deployment}{%
\subsection{Deployment}\label{deployment}}

\textbf{gateway/app.py} and \textbf{gateway/cloud\_app.py} are two
separate FastAPI services. They correspond to an edge-side gateway and
a cloud pod. \textbf{CloudClient} is the only component that connects
these two services, using real HTTP requests. The GCP multi-region
deployment script (code/deploy/gcp-up.sh) provisions three VMs: one
cloud pod, and two edge-side gateways in different regions. Each edge
machine runs its own \textbf{CascadeController}, agent, and edge model,
all co-located in the same process, so there are no network calls
between them. This is similar to a sidecar, but the key point is that
the agent here is not a separate remote service adding another network
layer. The cloud connection only opens once a request is actually
routed to the cloud.

A second, real Kubernetes deployment path exists alongside this one.
\textbf{code/deploy/gke-up.sh} and \textbf{gke-update.sh} provision one
small GKE cluster per region (europe-west2 cloud, europe-west4
near-edge, australia-southeast1 far-edge). They deploy the same three
services through real \textbf{kubectl}-managed
\textbf{Deployment}/\textbf{Service} manifests
(\textbf{code/k8s/cloud.yaml}, \textbf{orchestrator.yaml},
\textbf{gateway.yaml.tmpl}), rather than using \textbf{docker run} on a bare
VM. A single Kubernetes cluster cannot span these three regions,
because etcd consensus is not built for the roughly 250ms RTT to the
Sydney region. So cross-region calls stay at the HTTP layer, just as in
the Docker path above, only now between GKE clusters instead of bare
VMs. Prometheus and Grafana are deployed the same way, as real
Kubernetes workloads in the cloud region cluster
(\textbf{code/k8s/prometheus.yaml.tmpl}, \textbf{grafana.yaml}),
scraping \textbf{prometheus\_client} metrics exposed at \textbf{/metrics}
on every service across all three regions.

This deployment shape is not something LiteLLM or Portkey are built
for. Both route between cloud-hosted model providers, so their
deployment unit is just the gateway process itself. Neither has an
equivalent to a resource-constrained edge tier running its own model,
its own CascadeController, and its own agent co-located with it.
Comparing this project against them on ``does it beat a production LLM
gateway'' (Section~\ref{literature-survey}) is fair on the routing-decision axis both
address. But the edge/cloud split itself is a problem those gateways
were never designed to solve.


\hypertarget{orchestration-pattern-classification}{%
\subsection{Orchestration pattern
classification}\label{orchestration-pattern-classification}}

Microsoft's Azure Architecture Center taxonomy names five multiagent
orchestration patterns (sequential, concurrent, group chat, handoff,
magentic) plus a lower-complexity single-agent-with-tools tier, and
recommends using the lowest tier that reliably meets the requirement
(Microsoft, 2026). This project's design is a hybrid across that
taxonomy, split by execution path, summarised in
Table~\ref{tab:orchestration-hybrid}.

The per-request fast path sits at the single-agent-with-tools tier.
Bronze, Silver, and Gold (Section~\ref{dynamic-medallion-pipeline}) are
deterministic transforms, not agents, so the pipeline feeding them
into the policy matches the guide's sequential pipeline (and its
non-agentic ancestor, Pipes and Filters). One agent sits at the end of
it: the PPO-based \textbf{AgenticOrchestrator} (Section~\ref{ppo-agent}),
reading whichever Gold slots the MCP skill interface
(Section~\ref{mcp-skill-interface}) exposes. There is no second agent
and no peer coordination on this path, matching the guide's own advice
to avoid multiagent overhead where latency is the whole point.

The governance-time path adds a second decision-maker. The Policy
Orchestration Layer (Section~\ref{policy-orchestration-layer})
proposes a reuse/fine-tune/train-new decision, and the LLM governance
review (Section~\ref{llm-governance-review}) checks it against the
same client scenario, a maker-checker loop, the Azure guide's group
chat sub-pattern. Two details diverge from the pattern as written: the
check runs once rather than repeating until satisfied, and it can only
escalate the proposal, never approve something more permissive, so a
hallucinated review wastes compute at worst instead of silently
authorising an under-provisioned policy.

The Azure guide itself treats a hybrid like this as the expected shape
of a real system, recommending combined patterns whenever different
stages of one workload have different coordination requirements.
